## Delivered

- `POST /api/v1/screenings/:id/reviews` accepts shortlist/reject/hold, trims and requires a 1–2000-character note, requires a completed run, and checks the frozen `expected_application_revision` field. Insufficient coverage permits a documented decision. Closed jobs and historical completed runs retain review access.
- Existing session/origin/CSRF/action guards and job-resource authorization protect review creation/history. Application row locking serializes decisions and resume replacement; stale or simultaneous same-revision submissions return `409 revision_conflict`. Each successful decision appends a review referencing its predecessor, updates only the application's stage/current-review pointer/revision, and appends audit in the same transaction. Neither run nor criterion results are modified. Audit metadata contains no human note.
- `GET /api/v1/applications/:id/reviews` returns bounded, stable chronological pagination with reviewer/run/person attribution and the supersession chain.
- `GET /api/v1/dashboard` reads a repeatable-read, read-only PostgreSQL snapshot. Job assignment scope applies to every count and list. Application/current-decision counts do not multiply with historical reviews or runs. Recent applications and run summaries are limited to ten items each; summary fields reuse T8.6's projection and omit inputs, source text, envelopes and private storage keys.
- `GET /api/v1/audit-events` is admin-only, supports exact action/resource type/resource ID/job filters, inclusive date-time bounds and stable chronological pagination (default newest first, page size 20, maximum 100). IDs remain decimal strings and `safe_metadata_json` is exposed as the frozen `safe_metadata` field. There are no audit mutation routes.
- Controllers/providers are registered through the already-composed reviews/dashboard modules. The read-only audit controller/provider live with the dashboard reporting module so the audit writer module and shared root composition remain untouched.

## Dashboard definitions and boundaries

“Latest” means the newest persisted run per application ordered by creation time, then generation and UUID for deterministic ties. `screening_failures` counts applications whose latest run failed, with one latest failure summary each; an obsolete failed run stops appearing after a newer run exists. `awaiting_review` counts applications whose latest run completed and whose current human review does not reference that run, including insufficient-coverage results and new results following an older decision. Applications with no run or a latest queued/running/retrying run remain in total/recent applications but are not actionable completed reviews. Current decision totals always follow `current_review_id`, so new AI runs cannot silently change human stage or erase decision counts. Historical review/run routes retain the full history.

Integration tests use only the existing harness-validated local `rms_ai_test` PostgreSQL database, random synthetic records, temporary private storage and ephemeral loopback HTTP servers. Review fixtures start with an actual T8.6 admission/execution against its authenticated deterministic fake AI service; additional aggregate-history fixtures are explicitly synthetic database rows and make no provider/provenance demonstration claim. There are no paid gateway calls. Temporary storage is removed by the harness; synthetic fixtures remain in the disposable test DB.

No T8.8 blocker remains. Browser review/dashboard/audit screens, complete demo seeds and full-stack operational journeys remain with their assigned later tasks.
