## Delivered

- Authenticated config, screening start, authorized detail/history and explicit retry routes using the frozen platform DTOs. Starts/retries return 202 and a Location header once persisted; batches contain at most ten unique applications and are all-or-none. Detail alone exposes the stored envelope/source; summaries omit source, private storage keys and input snapshots.
- Approved-JD admission with job/application/resume scope checks, open-job checks, canonical input identity, immutable content/criterion mapping, exact PDF identity, authenticated manifest pinning, transactional audit and outbox. Normal starts reuse matching nonfailed runs, even after idempotency expiry; matching failures require an explicit retry.
- Actor/route-scoped, persistent 24-hour idempotency with advisory serialization, exact response replay and key/body mismatch conflicts. Application locks serialize identity/generation allocation. Explicit retries retain historical failures and frozen inputs/config, refreshing the manifest only for `config_changed`; concurrent retries of the same failure share the new nonfailed generation.
- Short authenticated manifest refresh with full schema/fingerprint validation and last authenticated configuration fallback. Admission with no validated cached manifest returns 503 without creating a run. Login and CRUD do not wait for manifest loading. Redis unavailability still returns a durable queued run with degraded dispatch state.
- A one-second relay with PostgreSQL row locks/skip-locked claims, IDs-only queue payloads, deterministic run/delivery-generation job IDs, and transactional delivery marking. An enqueue-before-commit crash safely redelivers the same queue job. Queue connections are lazy and recover after an initially unavailable Redis instance.
- A separate BullMQ worker entry point with concurrency one, 240-second renewing BullMQ lock, database attempt token/lease and heartbeat. Execution rechecks requester account/role/job scope, approved JD/config/resume relationships and frozen file bytes, then sends authenticated multipart PDF/JD to the existing AI endpoint with request/run/fingerprint headers.
- Shape/provenance validation using the checked-in shared OpenAPI schemas, exact manifest identity, PDF and normalized-text hashes, the existing Python JD hash representation, criterion codes/weights/priorities, source page bounds and Unicode code-point quote offsets. Result/source/criterion insertion, completion and audit commit together only for the current unexpired token. Scores are preserved as returned rather than recomputed.
- At most two automatic attempts in PostgreSQL, with five-second exponential backoff plus jitter for transport/deadline, throttling and transient provider failures. Invalid inputs, authentication, schema/provenance errors and configuration drift terminate immediately. Safe DB errors/history and retained BullMQ failed jobs expose failures without provider text or secrets.
- Startup/periodic reconciliation reconstructs missing queued deliveries, makes due retries deliverable, and recovers expired worker leases or fails exhausted runs. Bounded cursor-based sweeps avoid starving later runs behind older queued work. Late success/failure/heartbeat from an expired or superseded token cannot publish.

## Fault-injection interpretation and boundaries

Integration tests use the harness-validated local `rms_ai_test` PostgreSQL database, synthetic PDFs/users, temporary private storage, ephemeral loopback fake AI HTTP servers, and unique `rms_ai_test_*` Redis prefixes. They exercise actual Nest HTTP/auth/CSRF, filesystem storage, PostgreSQL transactions/triggers, BullMQ, Redis and a child Node process; no paid gateway or live-provider success is claimed. The fake service produces schema-valid, visibly deterministic, insufficient-coverage results; it can inject HTTP status errors, delays and malformed provenance.

Redis restart is injected by dropping and restarting a local TCP forwarding endpoint while the real backing Redis data remains intact; this covers connection loss/reconnect with retained delivery state without interrupting other workers' shared Redis. Total Redis-loss recovery separately deletes only the test's own BullMQ namespace and rebuilds it from PostgreSQL; tests never issue FLUSHDB or restart the shared container. The killed-worker test uses a disposable Node process, not an agent or Orca helper. Lease expiry and HTTP deadlines are shortened by explicit DB/timer fault injection rather than waiting four/three minutes.

The successful warm-admission integration assertion is under one second, and its fake AI call count remains zero until execution. This is a local smoke assertion, not a production latency claim. Actual AI extraction/provider deadlines remain owned by T8.3; the Node adapter applies the configured 180-second HTTP deadline and database fencing independently.

The relay may run in both registered API and worker contexts; PostgreSQL locks serialize claims, so concurrent pollers remain safe without another leader service. Delivery generations handle Redis reconstruction independently of immutable run generations. Automatic retries are scheduled from DB state instead of BullMQ's retry counter, preserving the two-attempt bound across Redis loss and worker restart. Terminal queue entries remain retained as the MVP failed-job view.

Run `pnpm worker:dev` (or the existing built worker start script after building) with the normal validated API configuration. Tests explicitly suppress automatic timers and drive relay/recovery deterministically; normal runtime starts startup/one-second recovery and relay automatically. Existing shared root bootstrap/module registration, health response contract, migrations, storage and auth services remain in their prior owners' files.

No T8.6 blocker remains. T8.7 browser integration, later operational/health presentation, deterministic full-stack journeys and optional live-provider demonstration remain with their assigned tasks. External inference is not exactly-once after a crash; database fencing prevents duplicate persisted results and the two-attempt cap bounds repeat calls. Synthetic fixtures remain in the disposable test DB; PostgreSQL/Redis services are left running.
