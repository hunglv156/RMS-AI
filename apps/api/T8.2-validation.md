# T8.2 implementation and validation

Implemented in `m7-auth` on 2026-11-23. Changes are confined to the auth, users, audit-writer modules, their permitted tests, and this requested report; no schema, root bootstrap, manifest, lockfile, AI, or audit-reader changes. No commit or helper worker was created, and no secret environment file was printed, copied, or created.

## Delivered

- Local Argon2id login for all three roles, normalized email, generic credential errors, bounded password/input validation, ten login attempts per source IP per fifteen minutes, and bounded in-process throttle storage.
- Random 256-bit opaque sessions with only SHA-256 hashes persisted, eight-hour expiry, login rotation, logout, disabled-account/session revocation, password-reset revocation, and current database role checks on every request. Responses omit password hashes and prohibit caching.
- HttpOnly, SameSite=Lax, Path=/ cookies; Secure on HTTPS. Exact origin validation includes login; all authenticated mutations, including future multipart routes, require the session-bound `X-CSRF-Token`. `GET /auth/me` returns the same derived session CSRF token without storing its plaintext.
- Admin list/create/update accounts, password resets, role/disable changes, pagination validation, and serialized last-active-admin protection across simultaneous changes.
- Globally registered session/action guard, explicit deny-by-default role policy, reusable job/resource authorization following application/JD/run ownership and assignment joins, and linked/historical resume access checks.
- Append-only transactional audit writer, actor/request context, login/logout and denied-security events, and strict metadata allowlisting that rejects personal text, secrets and provider payloads.

## Interpretation and feature-owner handoff

`APP_ORIGIN` is a non-secret optional runtime setting, defaulting to `http://localhost:5173`; set it to the browser's exact origin when using `127.0.0.1`, another port, or HTTPS. Insecure non-local origins fail closed. The throttle is intentionally process-local for the specified single API process and thesis demo; restarting the API clears it. There is no distributed rate-limit subsystem.

Later feature controllers must annotate handlers with `RequireAction` from `auth/authorization.service.ts`; missing/unknown actions deny access. `AuthRequest.actor` comes from the current DB account, never request input. Inject `AUTHORIZATION_POLICY` for `assertAction`/`assertJobAccess`, or `JobAuthorization` for `assertResourceAccess` (application, screening, JD, resume); pass a transaction when operating transactionally. Filter list/count queries by reviewer assignments as well as checking detail access. A reviewer may download a resume linked through either a current application or a historical screening on an assigned job. Job-assignment mutation remains with T8.4.

Action names are explicit: shared `jobs.read`, `jd.read`, `applications.read`, `resumes.read`, `screenings.read`, `screening_config.read`, `reviews.read/create`, `dashboard.read`; admin/recruiter additionally `jobs.create/update`, `jd.create/update/submit/clone`, `candidates.read/create/update`, `resumes.create`, `applications.create/update`, `screenings.create/retry`; admin additionally `users.read/create/update`, `jobs.assign`, `jd.approve/return_to_draft`, `audit.read`; reviewer additionally `jd.approve/return_to_draft` with job access checked by the owning handler.

Inject `AUDIT_SERVICE` or `AuditWriter` and call `append(tx, event)` in the domain transaction. Metadata currently permits `role`, `previous_role`, `disabled`, `reason_code`, and validated `changed_fields`; later feature events can use empty metadata and their resource/job IDs. Never put candidate names, emails, CV text, passwords, session/CSRF tokens, or provider payloads into audit events. Global audit reading remains T8.8-owned. No remaining T8.2 blocker.
