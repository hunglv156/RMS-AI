# T8.5 implementation and validation

Implemented in `m7-candidates` on 2026-11-23. Changes are confined to the candidates, resumes and applications module/test directories and this requested report. No commit, helper worker, migration, contract, dependency, shared bootstrap or T8.4 handler change was made; no secret environment file was printed, copied or created.

## Delivered

- Candidate create/read/update with bounded contact/name validation, required synthetic/demo-public provenance, literal name search, stable pagination, role checks and transactional audit.
- Multipart PDF streaming to random exclusive temporary files; content type, `%PDF-` signature and inclusive 10 MiB limit; exact binary SHA-256; fsync and atomic UUID-key rename; private directory/file permissions; no client filename used as a storage path.
- Filesystem adapter implementing the frozen `ResumeStorage` interface, exported through `RESUME_STORAGE`. Storage keys are validated, directory ancestors/root symlinks rejected, and reads use `O_NOFOLLOW` plus regular-file checks. Upload/stream/parser/DB/audit failures remove new files, and filename/header output is sanitized.
- Immutable resume versions allocated under a candidate row lock. Public resume metadata omits the private storage key. Downloads use T8.2's job/resource authorization and audit writer before streaming, with attachment disposition, PDF content type, `nosniff` and private/no-store caching.
- Application creation/linking, job-scoped paginated name search and revision-checked replacement. Wrong-candidate/invalid resumes and closed-job creation are rejected; duplicates and stale revisions return 409; stage is never accepted in these mutations. Replacement leaves historical run references and bytes intact.
- Startup and hourly orphan reconciliation with a minimum one-hour grace period, DB-derived reference set and shared in-flight upload protection. Only recognized regular orphan/temp files are removed; referenced/recent/in-flight files, symlinks, directories and unknown names are preserved. Reconciliation failures log only a fixed operational message and do not prevent API boot.

## Interpretation and handoff

Candidate CRUD follows section 2.6 and the frozen routes: create/read/update, with no delete endpoint. Resume versions are exposed by upload metadata and application/run references; no additional global resume-list route was invented. Reviewer application lists/counts include the assignment predicate and reviewer downloads use the existing current-or-historical resume guard; global candidates and unlinked versions remain forbidden.

Upload validates type/signature/size; deeper parsing, encryption, page/render limits and invalid-document screening outcomes remain with the AI/screening owners. Revision replacement is permitted on an existing closed-job application because the plan explicitly blocks new applications, screenings and JD approvals there, while retaining historical records; it never changes a prior run or decision. There is no automatic candidate merging or real-PII import workflow.

`FILE_STORAGE_ROOT` must name a dedicated private directory with canonical, nonsymlink ancestors (for example macOS `/private/var/...` rather than `/var/...` if that ancestor is a symlink). Tests canonicalize only the harness-created temporary root; they target only the harness-validated local `rms_ai_test` database and use direct synthetic job fixtures rather than T8.4 handlers. Temporary storage is removed by the harness, while synthetic DB fixtures remain in the disposable test database.

Later owners can import `ResumesModule` for the `RESUME_STORAGE` token and read the pinned storage key from the DB internally; browser DTOs never contain that key or a static URL. `ResumesService.reconcile()` is also callable for an explicit operational sweep. Runtime storage permissions assume the specified single-machine API/worker deployment. No remaining T8.5 blocker; web UI, queue/AI execution and end-to-end operation remain with their assigned tasks.
