# T8.6b validation — first screening waited ~156 s in the outbox

## Summary

- **Reproduced.** The cause is a producer Redis socket that was silently dropped while idle. The delay was never tied to process startup.
- **Fixed** in `apps/api/src/queues/queue-runtime.ts`. Every ordering now dispatches within about 1 s of the 202, or within about 1 s of Redis becoming reachable.
- **Regression tests:** `apps/api/test/queues/startup.integration.test.ts`. All three fail on the T8.6 code and pass with the fix.

## What T8.10 actually saw

Evidence (read-only):

- **T8.10 session logs:** `api.log` and `worker.log` in the T8.10 scratchpad.
- **Job hashes:** the BullMQ job hashes still present in the shared Redis, `m7-foundation`, port 56379.

| Time (UTC)   | Event                                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------------------------ |
| 00:54:48     | API and worker started (`tsx watch`). Both logs show no warning afterwards.                                        |
| 00:27–00:55  | Last jobs added to `rms_screenings` before the gap.                                                                |
| 02:06:43     | "Lan Chi" screening admitted (outbox `created_at`). This is **72 min** after start, with no Redis traffic between. |
| 02:09:19.150 | Job `70f2e8d7…-1` is added to BullMQ (`timestamp`) and processed at once (`processedOn` +0.0 s).                   |
| 02:12, 02:19 | Later jobs are delivered without delay.                                                                            |

So the "first screening after stack start" was really the first screening after more than an hour of idle. The BullMQ worker was healthy throughout, and only `queue.add` was late.

## Root cause

1. Each process (API and worker) relays the outbox through one producer ioredis connection. That connection sends no traffic while no screening is pending.
2. Docker Desktop's port proxy (and NATs in general) drops idle connections without sending a FIN or RST. ioredis keeps reporting `status === "ready"`.
3. On every 1 s tick, `ensureQueue()` saw "ready" and did nothing. `queue.add` then failed with the 500 ms `commandTimeout`.
4. `relay()` **swallowed** that error. It set `attempts+1` and `last_error='dispatch_unavailable'` and returned normally, so `tick()` treated the tick as healthy and never logged "dispatch unavailable". The socket was also never replaced.
5. The stall ended only when the OS gave up retransmitting on the dead socket. That took about 2.5 min on this Mac; ioredis then saw `close` and reconnected on the next tick. Until then, neither relay could deliver. The BullMQ worker's own connections stayed alive because they poll Redis (blocking pop, stalled checks, lock renewals).

Two further startup defects turned up while testing the orderings:

- **Worker started while Redis is unreachable never consumes.** BullMQ caches the failed first connection, and its `run()` rejection was swallowed. The run stayed `queued` with the job sitting in `wait` for more than 200 s, until the worker was restarted by hand.
- **A tick could hang about 10–15 s.** This happened when a new socket accepted the TCP connection but never answered. Neither the ioredis ready check nor BullMQ's init is bounded by `connectTimeout` or `commandTimeout`. While `busy` was set, no relay ran at all.

## Fix (`queue-runtime.ts` only)

- **Producer health check.** Each tick sends `PING` before relaying (one command per second per process, 500 ms timeout). This keeps the socket from ever going idle and detects a dead one. A failed PING calls `resetProducer()`, which disconnects the socket and drops the Queue so a fresh connection is used in the same tick.
- **Bounded connect.** Connect plus BullMQ `waitUntilReady` is raced against a 1.5 s deadline. On timeout the producer is reset and the tick fails visibly instead of hanging.
- **Enqueue failures are no longer swallowed.** The outbox `attempts` and `last_error` update still commits, then `relay()` rethrows. `tick()` resets the producer and logs `Screening dispatch unavailable; durable work retained; N outbox event(s) waiting, oldest S s`. The log repeats every 30 s while degraded, and `Screening dispatch recovered` follows.
- **Worker startup.** The BullMQ `Worker` is created only after its own connection, which retries every 1 s, reaches `ready`. After 1 s it logs `Screening worker waiting for Redis…`, and then `Screening worker connected to Redis`.
- **Faster recovery after a blip.** `runRetryDelay` is lowered from 15 s to 1 s, so jobs are not held for 15 s after a Redis blip.
- **Lease visibility.** When a `running` run's lease has missed two renewals (its holder is gone), the log prints, once per attempt, `Screening run <id> is waiting on a worker lease that is no longer renewed; recovery in N s`.
- **Bounded reconcile.** `reconcile()` stops probing Redis for the rest of a pass after one failure, instead of paying the timeout once per queued run.

**Unchanged:** transactional outbox, `jobId = run-generation` idempotency, `SKIP LOCKED` relay, lease length (240 s), attempt tokens and fencing, retry budget, and the degraded 202. Every T8.6 acceptance test passes unmodified.

The idle-drop row is the T8.10 symptom. The test proxy never closes the dead socket, so "before" stalls indefinitely. On the real Docker Desktop proxy the OS eventually closed it, which gave the observed 156 s.

## Regression tests (`test/queues/startup.integration.test.ts`)

1. **Dead idle producer socket.** After a warm relay, the proxy black-holes the producer's socket, and the next relay must deliver within 2 s with `attempts=1`.
2. **Enqueue failure is visible.** With existing and new sockets black-holed, `tick()` must log exactly one warning: `Screening dispatch unavailable; durable work retained; N outbox event(s) waiting…`. The event stays durable and undelivered.
3. **Worker before Redis.** `startWorker()` is called while the Redis port is closed. Once the port opens, the run must be delivered and completed.

On the T8.6 code all three fail (1.99 s, 2.90 s and 7.83 s timeouts). With the fix they pass, and three consecutive runs of the queues suite were stable.

## Residual risks

- **Worker sockets.** The BullMQ worker's own sockets have no command timeout, because blocking commands cannot have one. They stay safe from idle drops only because they poll at least every 30 s. If an active socket is black-holed, the worker hangs until the OS closes the socket. This was not observed in T8.10.
- **Stale lease.** A run that was `running` on a killed worker still waits for its 240 s lease before recovery, by design. It is now announced in the log. Shortening it would weaken T8.6 fencing.
- **Shared queue prefix.** The shared compose Redis is used by several worktrees under the same `rms_screenings` prefix. A worker from another checkout on the same Redis can take this stack's job, find no run in its own database and complete it. Reconcile then has to redeliver it as a new generation. For the committee demo, run exactly one API and worker pair against that Redis.
