# T8.12 — Authorized candidate and actor display names

## Changes

Applications returned by create, replacement, per-job lists, and dashboard recent items now include `candidate_display_name`. Screening admission/reuse/retry, detail, history, dashboard pending reviews, and failures include the same name directly (including idempotency responses saved before this change), so pending items do not depend on appearing in the bounded recent application list.

Additive OpenAPI fields expose `ActorDisplay` (`id`, `display_name`, with no other properties): JD `created_by_actor`, `submitted_by_actor`, `approved_by_actor`, `returned_by_actor`; review `reviewer`; resume `uploaded_by_actor`; screening `requested_by_actor`. Existing ID fields remain intact. The latest JD return actor is joined from the existing immutable `jd.returned_to_draft` audit event, avoiding a migration; the admin audit endpoint and authorization policy are unchanged.

Web views consume the returned names. Reviewers no longer request candidate or user directories to resolve names. JD transitions, decisions, resume uploads, and screening detail/history show actor display names; the current user may have `(bạn)` appended. Reference IDs remain only in explicitly labeled record/provenance fields, never as people names. The mock client supplies the additive fields as well.

## Authorization and privacy evidence

`test/reviews/display.integration.test.ts` verifies assigned reviewers receive candidate names in applications, run detail/history, and dashboard entries; actor objects contain only `id` and `display_name`; no email, phone, or role fields are added. It also verifies candidate listing/detail remain 403, unassigned jobs/run/history/resume access remain 404, unlinked resumes remain 404, audit reading remains 403 for reviewers, and assignment revocation removes access immediately. Existing application, dashboard, and JD workflow tests additionally verify candidate names, hidden candidate exclusion, and return actor attribution.

Component coverage includes reviewer application names without candidate/user calls, a pending review whose application is outside the recent list, all JD transition actors including another user, and decision attribution. E2E assertions verify candidate names in application/admission responses and reviewer headings, and exact reviewer identity objects.
